## 2. Thiết kế bộ test hiện hành

- Unit tests kiểm tra validation, policy và renderer/exception handler thuần, không DB/network.
- Contract tests kiểm tra route, schema, JWKS và framework/config contracts; không gắn DB khi không cần.
- Integration tests dùng DRF APIClient cùng ORM/PostgreSQL thật cho ràng buộc, transaction,
  audit/outbox, JWT rotation/replay và Axes. Không thay PostgreSQL bằng mock/SQLite cho các ca đó.
- Ba workflow trong `tests/test_flows.py` dùng Requests Session và fixture `live_server`
  của pytest-django. Đây là HTTP trên Django test server, tự cấp port và test database,
  được pytest phát hiện trong lệnh chạy mặc định.
- Test lỗi độc lập dùng parametrization để bao phủ các nhóm dữ liệu đầu vào. Fixtures
  chuẩn bị dữ liệu và đóng HTTP sessions; pytest-django quản database lifecycle.
- Test external adapter có mock HTTP rõ ràng. Google/GitHub/R2 thật, Kafka ACK, gửi thư và
  consumer liên service cần acceptance riêng; không đánh dấu Pass từ local mock.

Fixtures chỉ làm setup/cleanup; assertions nằm trong test. Marker unit/integration/contract
phân loại mỗi pytest item; http là tập con integration. APIClient cùng ORM là integration,
không gắn nhãn unit. Không dùng transaction=True khi test không cần multi-thread/commit.
Test logging quan sát logger thật bằng caplog; chỉ mock dependency tại boundary cần fault.

Helper dùng chung ở `tests/helpers.py`; không import từ module `test_*` khác và không
đọc `APIClient._credentials`. Login/API tests lấy credential từ response của thư viện.
Unit và integration có thể kiểm nhiều assertions cho cùng một hành vi; pytest không yêu
cầu một assertion/test. Các ca input lỗi độc lập dùng parametrization; vòng lặp trạng
thái Axes hoặc nhiều thiết bị trong cùng workflow được giữ. Marker/config sai làm pytest
báo lỗi nhờ `--strict-markers --strict-config` mặc định.

Các luồng trọng tâm gồm PBKDF2 login, response headers, refresh replay/concurrency,
provisioning permissions, admin mutations và DB constraints; xem
[cấu hình và kiểm thử](../identity-service/README.md#cau-hinh-va-kiem-thu).

Các workflow được chia thành
đăng ký/phiên, reset, và change password để khi fail biết luồng nào bị lỗi. Chỉ giữ chuỗi
request dài khi cần kiểm tra đúng một workflow; không gom mọi tính năng vào một test lớn.

Nguồn chuyên môn đã đối chiếu:
[pytest fixtures](https://docs.pytest.org/en/stable/how-to/fixtures.html),
[parametrization](https://docs.pytest.org/en/stable/how-to/parametrize.html),
[pytest-django live_server](https://pytest-django.readthedocs.io/en/latest/helpers.html#live-server),
[DRF testing](https://www.django-rest-framework.org/api-guide/testing/).

## 3. Quy ước chung và dữ liệu kiểm thử

- [Use case](../diagram/identity-service/usecase.md), [sequence](../diagram/identity-service/sequence.md) và [chỉ mục bàn giao](../diagram/identity-service/README.md) nối từng UC với API/bảng/test.
- Fixture GitHub success stub/contract-test endpoint Integration3.3.2.1 với operation_id/user_id/provider/expiry khớp; chỉ Integration có outbound provider HTTP. Không mock /user ngay trong Identity rồi gọi đó là kiểm boundary.
- Fixture OAuth success phải thực hiện start, giữ cookie context và gửi state/redirect_uri hợp lệ; stub provider code khác nhau và nonce đúng. State/nonce/expiry sai chỉ dùng trong ca lỗi tương ứng; không bỏ start để làm test link thành công.
- Fixture outbox.data lưu toàn envelope; assert dữ liệu nghiệp vụ ở outbox.data["data"], assert trace_id/event_id không đổi khi publish lại. Mail expiry độc lập, secret=null khi hết hạn.
- Family TTL7 ngày tuyệt đối, rotation không gia hạn. Avatar confirm success phải có receipt Redis đúng owner/type/size và R2 HEAD khớp.


- Source có đầy đủ các nhóm pytest local. Bảng TC chỉ ghi Pass khi đã rà contract và mapping; các dòng khác còn là tiêu chí cần xác minh.
- MSSV chỉ có một nguồn sửa ở Identity; enrollment/projection Classroom dùng user_id. Register không nhận student_id; provisioning có quyền mới gán mã.
- Fixture user phải có `username`, `users.student_id`, `users.account_status`. Mật khẩu đặt bằng `set_password()`; field Python `password` ánh xạ cột DB `password_hash`. Không đặt MSSV trong UserProfile.
- Một device giữ một session_id/token_family. Rotation cập nhật hash/jti trên row này và blacklist token cũ; không tạo session row ROTATED riêng.
- Fixture audit dùng `actor_id`, `target_user_id`, `details`; không dùng `actor` hoặc `metadata`.
- Các ca Identity provisioning gọi `POST /api/v1/internal/users/provision-students` với JSON `students`, actor JWT hợp lệ, X-Service-Key và Idempotency-Key. CSV/XLSX, quyền lớp và enrollment được test trong Classroom; ca liên dịch vụ phải kiểm cả hai DB qua API.
- Mọi response nghiệp vụ có đủ `success,message,data,meta,error`; bảng chỉ nêu phần cần assert, không phải response JSON đầy đủ. `error.details` là mảng `{field?,issue}`, thông điệp chung nằm ở `message`. JWKS là ngoại lệ: trả `{"keys":[...]}` trực tiếp.
- Giao dịch/khóa/trigger phải chạy PostgreSQL 16, dùng `pytest.mark.django_db(transaction=True)` và kết nối riêng cho request đồng thời. SQLite và test mock không chứng minh được khóa hoặc commit.

## 5. Chạy test bằng pytest

Từ `apps/identity-service`, unit tests chạy không cần database. Suite integration/full
cần PostgreSQL test connection (user có quyền tạo test DB), và Redis cho các ca dùng Redis:

```powershell
uv sync --locked
uv run --locked pytest -q
uv run --locked pytest -q -m unit
uv run --locked pytest -q -m integration
uv run --locked pytest -q -m contract
uv run --locked pytest -q -m http tests/test_flows.py
```

Ví dụ chạy ba test HTTP trên máy Windows bằng PostgreSQL Docker đang publish55432,
nạp credential từ root .env:

```powershell
$env:POSTGRES_HOST = "127.0.0.1"
$env:POSTGRES_PORT = "55432"
uv run --locked --env-file ../../.env pytest -q -m http tests/test_flows.py
```

Suite đầy đủ còn cần `IDENTITY_TEST_REDIS_URL` trỏ tới Redis kiểm thử có thể kết nối.
Không dùng Redis production; các bài test Redis dùng DB15 riêng. Trong lần kiểm chứng này,
suite chạy trong thư mục source test riêng của container hiện có, kết nối PostgreSQL/Redis
qua mạng Compose; không recreate container hoặc đổi DB của ứng dụng đang dùng.

Pytest-django tạo `test_identity_library_auth`, quản lý transactions/flush và dọn test DB.
`live_server` chạy server ở background thread nên dùng transactional database. RSA/mail
keys trong `tests.settings` chỉ dành cho kiểm thử. Vì vậy đây là kiểm tra code qua HTTP thật
của Django test server, không phải nghiệm thu Gunicorn hoặc key mount của deployment.

Test đọc encrypted outbox của DB test để lấy mã activation/reset; gửi mail Notification,
publisher Kafka, provider thật và Project/Classroom consumer vẫn Not Executed.
Lệnh `--junitxml=<path>` tạo artifact kết quả máy đọc được.

Mỗi case kiểm status/Content-Type/envelope, data schema và UUID/date-time. JWKS keys ở
root. Các test lỗi trong test_cookie_security/test_registration/test_password_errors,
test_login/test_rotation/test_provisioning/test_api_completion bổ sung kỳ vọng side effects;
12 thao tác cần Bearer có401/error schema/WWW-Authenticate riêng. Ba workflow HTTP và
concurrency/rollback vẫn chạy trong full suite. Không suy luận rằng mỗi API đã có mọi
tổ hợp input/status hoặc25/25đồng nghĩa mọi nhánh đều được thực thi.
